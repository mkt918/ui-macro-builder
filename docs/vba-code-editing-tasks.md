アプリ全体のQA診断（要件照合＋利用シナリオ＋Web観点チェック）で見つかった10件の指摘を、

1. **変数名を「i」/「arr」にすると生成VBAが二重Dimでコンパイル不能** →

## 改善提案の実装（2026-09-24、QA診断で挙げた3件）

## バグ修正（2026-09-24 その2）: 自動インデントの競合を修正

ユーザー報告「自動インデントの処理がおかしい」を受けて調査し、**2つの連鎖したバグ**を
実際のタイピングをシミュレートして発見・修正した。

### バグ1: Enter直後のレースコンディション
`Next`/`Loop`/`End If`/`Else` などの閉じキーワードを打ち終えた直後、間髪入れず
Enterキーを押すと、キーワード入力を検知して行のインデントを戻す処理
（`dedentClosingKeywordLine`、change イベント経由で `setTimeout(0)` により非同期実行）
が**まだ完了していない状態**を Enter 側のインデント計算が読んでしまい、
次の行にズレたインデントがそのまま引き継がれる不具合があった。

再現（実ブラウザでタイピングを再現）:
```
For i = 1 To 5 [Enter]
If i > 2 Then [Enter]
MsgBox i [Enter]
End If[Enterを間髪入れず]
Next i
```
修正前の結果:
```
For i = 1 To 5
    If i > 2 Then
        MsgBox i
        End If      ← 本来4スペースのはずが8スペースのまま
        Next i      ← 本来0スペースのはずが8スペースを引き継ぐ
```

修正: `handleCodeEnterKey()` の先頭で `dedentClosingKeywordLine()` を同期的に
呼んでから、インデント計算を行うようにした。

### バグ2（修正1の副作用として発覚）: 二重デデントによる過剰な字下げ解除
バグ1を直した直後の検証で、今度は `End If` が **0スペースまで**戻ってしまう
新しい不具合が発生。原因は `dedentClosingKeywordLine()` が「呼ばれるたびに
無条件で4スペース減らす」実装で**冪等でなかった**ため、同期実行（Enterキー側）と
非同期実行（change イベント経由の setTimeout）の両方が同じ行に対して発火し、
8スペース分（2段階）減ってしまっていた。

修正: `dedentTimer`/`dedentTimerLine` でどの行に対する非同期デデントが保留中かを
追跡し、Enterキー側で同期的にデデントする前に、同じ行への保留中タイマーが
あればキャンセルするようにした（`src/app.js`）。

### 検証
実ブラウザでタイピングを再現し、以下を確認:
- `For`/`If...Then`/`End If`/`Next` のネスト（素早くEnter）: 修正前は末尾2行のインデントが
  ズレる不具合を確認 → 修正後は正しいインデント（`For`=0, `If`=4, `MsgBox`=8, `End If`=4, `Next`=0）
- `If...Then...Else...End If`（`Else`の後はゆっくり待ってからEnter＝非同期デデントが
  先に完了するケース）: 正しく動作
- `Do While...Loop`（素早くEnter）: 正しいインデントで生成され、`vba-parser.js` で
  `loop_while` ブロックへの変換にも成功することを確認
- 既存のTabスニペット展開（for/ifelse）: 壊れていないことを確認
- コンソールエラーなし
